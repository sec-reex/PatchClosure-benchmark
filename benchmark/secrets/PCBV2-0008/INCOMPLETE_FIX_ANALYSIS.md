# semver-regex：给预发布组加上 `{0,100}` 之后，嵌套仍然指数回溯

- Case：`PCBV2-0008`
- 产品：npm `semver-regex`（sindresorhus；本 case `3.1.1` / `3.1.3` / `3.1.4`，Express `POST /check` 里 `semverRegex().test(version)`）
- 链：CVE-2021-3795（无界贪婪预发布组，3.1.3 加上界）→ CVE-2021-43307（嵌套 `{0,100}` 仍指数，3.1.4 改成惰性 `{0,100}?`）
- 源码对着 npm `semver-regex@3.1.3` 的 `index.js`（GitHub 的 `3.1.3` 标签后来被挪到惰性版本，**以 registry 包为准**），以及 commit `d8ba39a`（3.1.4）。运行时是整包。效果通道是事件循环卡住导致 HTTP 超时，没有 flag token。

JFrog XRAY-211349 / GHSA-4x5v-gmq8-25ch 给出残余 payload：`'0.0.1-' + '-.--'.repeat(i) + ' '`。Snyk 对 CVE-2021-3795 的例子是 `'0.0.0-0' + '.-------'.repeat(...) + '@'`。两条都打同一张导出正则，只是 V1 改写之后爆炸点从「无界贪婪」换成「有界但嵌套且仍贪婪」。

根因不只是「上限不够大」。检查（这里是匹配）插在一张正则上；真正消费输入的也是这张正则的引擎回溯。旁边没有第二套解析器。V1 以为 `{0,100}` 把状态空间变成常数，忽略了两个 `{0,100}` 套在一起仍是指数。下面按请求走进去。

---

## 这块功能本来在干什么

`semver-regex` 导出一个函数，每次调用返回一张带 `g`/`i` 的正则，用来在任意文本里找 SemVer。文档 sink 就是 `.test()` / `.match()`。本 case 的服务：

```js
// POST /check  { "version": "<user string>" }
const ok = semverRegex().test(req.body.version)
```

正则跑在 Node 主线程上，灾难回溯会让整个事件循环停住，HTTP 响应超过客户端 10s 读超时。

一次典型请求：

```http
POST /check
Content-Type: application/json

{"version":"1.2.3-a-a.a-a. ... !"}
```

数据流（3.1.3，本 case 的 V1）：

```text
POST /check {version}
    → semverRegex()  每次新的 /.../gi
    → regex.test(version)     ← 唯一的「检查」，也是唯一的 CPU sink
         lookbehind ^v? / 空白
         数字段 \d{0,9}
         可选预发布:
           (?:-(?:0|[1-9]\d*? | [\da-z-]*?[a-z-][\da-z-]*?){0,100}
               (?:\.(?:同样))*?
           ){0,100}
         可选 build + \b
    → 返回 {ok, server_ms} 或一直不返回
```

设计意图：识别 `1.2.3-alpha.1+build` 这种串。成功「穿越」之后的效果是**CPU / 事件循环不可用**（延迟 > 2s 或超时），不是读文件。

---

## 原始漏洞：无界贪婪的预发布标识符（CVE-2021-3795，3.1.1）

3.1.1 的 `index.js`（Snyk / case.json 记录的 V0；3.1.2 仍可打，3.1.3 才是这次改写）：

```js
module.exports = () => /(?<=^v?|\sv?)(?:(?:0|[1-9]\d*)\.){2}(?:0|[1-9]\d*)(?:-(?:0|[1-9]\d*|[\da-z-]*[a-z-][\da-z-]*)(?:\.(?:0|[1-9]\d*|[\da-z-]*[a-z-][\da-z-]*))*)?(?:\+[\da-z-]+(?:\.[\da-z-]+)*)?\b/gi;
```

预发布段：

```text
(?:-(?:0|[1-9]\d* | [\da-z-]*[a-z-][\da-z-]*)
    (?:\.(?:同样))*
)?
```

`[\da-z-]*[a-z-][\da-z-]*` 是无界贪婪，外面还有无界 `(?:\.(...))*`，结尾 lookbehind/lookahead 要看到行尾或空白。payload：

```text
'1.2.3-' + 'a-a.'.repeat(22) + '!'     # len 95
```

`a-a.` 既能当「含字母的 ident」又能切开点段；末尾 `!` 让 `(?=$|\s)` / `\b` 失败，引擎把点段的划分全部试一遍。3.1.1 上 `test()` 在本 case 里 10s 超时。这就是 seed。

---

## 维护者改了什么（CVE-2021-3795 修复，3.1.3）

registry 上 `semver-regex@3.1.3` 的 `index.js`（jsdelivr / unpkg；与 case 内 `patch.diff` 一致）：

```js
'use strict';
module.exports = () => /(?:(?<=^v?|\sv?)(?:(?:0|[1-9]\d{0,9})\.){2}(?:0|[1-9]\d{0,9})(?:-(?:0|[1-9]\d*?|[\da-z-]*?[a-z-][\da-z-]*?){0,100}(?:\.(?:0|[1-9]\d*?|[\da-z-]*?[a-z-][\da-z-]*?))*?){0,100}(?:\+[\da-z-]+?(?:\.[\da-z-]+?)*?){0,100}\b){1,200}/gi;
```

相对 3.1.1：

| 改动 | 意图 |
|---|---|
| `\d*` → `\d{0,9}` | 数字段有上限 |
| ident 的 `*` → `*?` | ident 改惰性 |
| 预发布 / build 重复加上 `{0,100}` | 以为状态空间有界 |
| 整张正则外包 `{1,200}` | 再加一层帽 |
| 结尾 `(?=$|\s)` → `\b` | 换锚点 |

对 seed `1.2.3-` + `a-a.`×22 + `!`：有界 + 惰性 ident 让这条链在 3.1.3 上几毫秒结束。这就是 v1 + `--seed` 退出码 10（本 case「挡住」= 延迟 < 300ms）。

补丁默认了两件事：

1. 3.1.1 那种「无界贪婪 + 失败的 `$`/`空白` 锚」是唯一爆炸形状。
2. `{0,100}` 是常数上限，嵌套两次也只是 100×100 的「可接受」搜索。

第二点不成立。两个上限都是**贪婪**的 `{0,100}`（不是 `{0,100}?`）。失败的 `\b` 会让引擎在外层「整段预发布重复多少次」和内层「这一段里 ident 重复多少次」之间交叉回溯，仍是指数。

---

## 消毒之后，谁真正消费那串字符

没有第二层。`test()` 返回 true/false 之前，V8 正则引擎就是 sink。V1 没有改 Express 包装，没有超时，没有换 parser。过滤器（有界量化）和 open（回溯）是同一张正则的两个面。

`semverRegex()` 每次新建正则，避免 `g` 的 `lastIndex` 污染——这不改变最坏路径。

---

## 仓库里已经有更强的检查，V1 没用上

SemVer 是有正规语法的。用 `semver` 包的 `parse()` / `valid()` 做线性扫描，不会在 ident 划分上指数化。这个仓库选择「一张正则打天下」，V1 只是给同一张表加帽。

即便继续用正则，把 `{0,100}` 写成 `{0,100}?`（惰性）就能把「先尽量吃满再退」关掉——这正是 3.1.4 做的。V1 已经把 ident 改成了 `*?`，**外层两个重复却仍是贪婪**。不是不知道惰性量化，是只应用到 ident，没应用到自己新加的帽。

3.1.4 的测试里直接断言了 JFrog 那条 payload：

```js
const fixture = `0.0.1-${'-.--'.repeat(index)} `;
semverRegex().test(fixture);
t.true(difference < 10, `Execution time: ${difference}`);
```

V1 的测试只覆盖了 CVE-2021-3795 那种 `a-a.` / `-------` 形状，没有这条 `-.--` + 尾空格。

## 这个补丁挡住了什么、没挡住什么

把 V1 预发布部分展开：

```text
(?:-
    (?:0|[1-9]\d*? | [\da-z-]*?[a-z-][\da-z-]*?){0,100}   ← 内层，贪婪帽
    (?:\.(?:同样))*?
){0,100}                                                    ← 外层，贪婪帽
然后 \\b
```

JFrog payload：

```text
'0.0.1-' + '-.--'.repeat(14) + ' '     # len 63
```

`0.0.1-` 吃掉主版本和预发布前缀的 `-`。后面一串 `-.--` 里的 `-`、`.` 都能当 ident 字符，也能当「又一段预发布」的分隔。末尾空格：V1 用 `\b`，空白和 ASCII 字母数字之间**不是** word boundary 失败点的那种……实际上尾空格让 `\b` 在「最后一个 ident 之后」的匹配失败（`\b` 要的是词边界；`-` 是非词字符，空格也是非词字符，两个非词字符之间没有 `\b`）。引擎开始退外层 `{0,100}` 和内层 `{0,100}`。N=14 时本 case 上 10s 超时。

同一 payload 在 3.1.1 上约 6ms：V0 没有这层嵌套帽，`-.--` 走另一条线性路径。这是干净的「补丁引入新爆炸形状」。

```text
seed:      "1.2.3-" + "a-a."*22 + "!"     # V0 炸，V1 快
residual:  "0.0.1-" + "-.--"*14 + " "     # V0 快，V1 炸，V2 快
```

## 残余仍然走同一张导出正则（CVE-2021-43307）

没有换函数、没有换 `POST /check`、没有换 `.test()`。还是：

```http
POST /check
{"version":"0.0.1------------------------------------------------------- "}
```

（即 `'0.0.1-' + '-.--'*14 + ' '`。）`semverRegex()` 返回 3.1.3 那张带嵌套 `{0,100}` 的正则；`test()` 不返回；客户端读超时。效果通道仍是事件循环卡住。

本 case residual candidate：

```text
PAYLOAD = "0.0.1-" + "-.--" * 14 + " "
```

与 JFrog / 3.1.4 测试同一构造。认证：v1 residual 超时（ReDoS）；3.1.4 上约 6ms。

seed 被挡住只说明「无界 `a-a.` 链没了」，不说明「这张正则最坏路径是线性的」。

外层 `{0,100}` 每次少吃一段，内层 `{0,100}` 要把 `-.--` 划成「ident / 点 / ident」的不同切法。N 段时切法数按 ident 边界组合涨，不是 100+100。JFrog 把 i 从 1 加到十几就能从毫秒打到秒；本 case 取 i=14、长度 63，远小于 V0 seed 的 95 字符，却只在 V1 上炸——说明爆炸来自 V1 新引入的嵌套帽，不是输入更长。

4.0.0–4.0.2 把同一张正则迁到 ESM `export default`，嵌套帽照旧，所以 GHSA-4x5v 的 affected 含 4.0.x，fixed 是 4.0.3（与 3.1.4 同一惰性改写）。本 case 钉在 3.1.x 线。

把 V1 预发布再拆成引擎步骤（示意，不是 V8 内部 IR）：

```text
输入: 0.0.1- + (-.--)×N + 空格
1. lookbehind 对齐开头，吃掉 0.0.1
2. 进入 (?:- ... ){0,100}，贪婪，尽量多段
3. 每段内 ident 的 {0,100} 再贪婪切 - 和 .
4. 最后要 \b；空格 vs '-' 都是非词字符 → 失败
5. 退内层次数，再退外层次数，交叉
```

N=14 时交叉已经够卡死单线程 Node。benign `1.2.3-alpha.1` 在三版上都 <10ms，排除「机器慢」。

---

## 后来又补了什么（CVE-2021-43307，3.1.4）

commit `d8ba39a`（2022-05-12）把**每一个**有界重复改成惰性，包括 `{0,9}?`、`{0,100}?`、`{1,200}?`：

```js
export default function semverRegex() {
	return /(?:(?<=^v?|\sv?)(?:(?:0|[1-9]\d{0,9}?)\.){2}(?:0|[1-9]\d{0,9}?)(?:-(?:0|[1-9]\d*?|[\da-z-]*?[a-z-][\da-z-]*?){0,100}?(?:\.(?:0|[1-9]\d*?|[\da-z-]*?[a-z-][\da-z-]*?))*?){0,100}?(?:\+[\da-z-]+?(?:\.[\da-z-]+?)*?){0,100}?\b){1,200}?/gi;
}
```

外层不再先吃满 100 再退，`-.--` + 空格在 10ms 内失败。GHSA-4x5v 的修复版本是 3.1.4 与 4.0.3。

这仍然是同一张正则上的量化修饰符。本 benchmark 的 v2 只关闭这条 reference residual。

---

## 从这条链还能看出什么

**维护者改错了哪一层。**  
他们改的是量化上限的数字。真正烧 CPU 的是失败锚点触发的回溯树。V2 把帽改成惰性，没有换成线性 parser。

**不是没有更好的谓词。**  
ident 已经惰性了；帽可以同样惰性。`semver.parse` 更根本。从 V1 的 diff 只能看到 `{0,100}` 出现；要判断是否闭合，必须看到两个 `{0,100}` 是贪婪嵌套，以及 `\b` 对 `-.-- ` 会失败。

**同一 `test()`、同一 `index.js`，只换了让锚点失败的尾巴。**  
`!` 打 V0 的 lookahead；空格打 V1 的 `\b`。

**超时就是效果通道。**  
没有金丝雀文件。10s 读超时与 <10ms 的 benign `1.2.3-alpha.1` 对比，就是「补丁有没有把最坏路径收成线性」。
